# internal/server

The HTTP layer: it turns the contract in `openapi.yaml` into handlers, and every other package of `internal/` is below it (only `cmd/` imports this one).
It is split into real Go packages, one folder per family, around a shared kernel. What stays in package `server` is the composition root: the server itself, its routes and what is not a family (authentication, CORS, the settings, the content mode, the OpenAPI document). Its files start with `core_`; the test of a file sits next to it with the same name plus `_test.go`.

## Packages

- `api/` (package `api`): the kernel. The JSON and error helpers (`WriteJSON`, `WriteError`, `APIError`, the `Code*` constants, `WriteRoutingError`, `WriteAssistError`, `NeedsLocalMemory`), the signature of route registration (`HandleFunc`) and the catch-all of `/api/` (`CatchAll`), the patterns more than one family checks (`ProjectIDPattern`, `LanguagePattern`), the event log and the server-sent-events writer (`EventLog`, `SSEWriter`: runs and downloads stream through them) and a few pure helpers (`Refuse`, `LastLines`, `AtomicWrite`, `DirExists`, the YouTube address and `yt-dlp` error, the Ollama test). It imports no other package of the server.
- `modelcat/` (package `modelcat`): the shape of an entry of the model catalog (`Entry`, `File`, `Timing`, `Preset`...). The catalog itself (`catalog.json`) is embedded by `server`; the families that read it share only these types.
- `assistant/` (package `assistant`): the prompt assistant, describing a reference, speech, the library of motion references and the model providers. It asks the server for what it needs through its `Host` interface; `hosts.go` in `server` implements it. A package has `New(host)` and `Register(handle)`; `Server.routes()` calls them.
- `workspace/` (package `workspace`): projects and runs, one family because they use each other. The project API and everything that belongs to a project (sources, clips, library, recipe, importing and exporting, artifacts, storage, stored pages of motion graphics, videoclips), the run manager (queue, lanes, history in the database, sampler, estimates, calibration, statistics), the reviews, the run-event stream, the metrics, the monitoring, the environment report and the availability of each task. It also keeps what the other families need to create a project of their own: the *managed projects* of the generation API, the image and video edits and the music-motion pieces (`ManagedInfo`, `CreateManaged`, `RemoveManaged`...) and the label of who asked (`clientlabel.go`). Its `Host` is what it needs of the rest (the content mode, the catalog, the music services, the keys, test seams); `workspaceHost` in `hosts.go` implements it, and `testing.go` has the few hooks the tests of `server` use to drive runs without a pipeline.
- `models/` (package `models`): models and the files they live in: the inventory of assets (models, voices, adapters), the download manager (queue, progress, conversion of a checkpoint), the Civitai lookup of the private edition and the vision service of the video-edit tools (client side).
- `generation/` (package `generation`): the one-call generation API (a video, a picture edit), the plan that picks the models for a machine, the inputs and the presets, the video-edit tools with their library of motions and the Blender scenes.
- `music/` (package `music`): songs and the music studio: the music-motion API and the drafts of its parts, listening, waveforms, song analysis, recognition (CLAP and MuQ), dictation, loudness, and the engines HeartMuLa, DiffRhythm2, CLAP and the vision service with the start and stop of their services. `testing.go` has the hooks the tests of `server` use.
- `prompts/` (package `prompts`): the store of prompt presets served at `/api/prompts`: a list that can be paged and searched, one preset read and changed, and the import of bundles. It keeps nothing in memory: the presets are rows of the database (`internal/prompts`), which `veritmo prompts fetch` writes too.
- `servertest/` (package `servertest`): the helpers the tests of `server` and of its sub-packages share (`DoJSON`, `Call`, `WaitUntil`, `IsolateSettings`..., the contract checker that walks an answer against `openapi.yaml`) and `servertest/stack`, the stack of families a family's tests run over. Only tests import it.
- **The state of the server is in its database** (see [docs/DATA_STORE.md](../../docs/DATA_STORE.md)): `core_data.go` (`DataRegistry`) is the one place that tells the database what each area owns, its migrations and its importers. `Config.DatabaseState` (set by `veritmo serve` only) makes `New` install the process-wide handles on that database once the state kept in files has been imported: the settings (`settings.UseSource`) and the catalog of HyperFrames blocks the music motion layers read (`musicmotion.BlockStore`); it gives them back at shutdown. A test leaves it off, so one test cannot leave its database behind for the next.
- Rules: a sub-package never imports `server`; `api` and `modelcat` import no sibling; the others import `api` and only the siblings below them (`internal/architecture` checks it). The stack is `api` < `assistant` < `workspace` < `models` < `generation` < `music`. A test that needs the whole server (`newTestServer`, `s.Handler()`, the contract in `openapi.yaml`, the settings, the content mode) stays in `server` as an HTTP-level test; the tests of a family run over the stack of families below it (`servertest/stack`, `harness_test.go`).
