# Management HTTP API (`veritmo serve`)

`veritmo serve` starts a local HTTP server that exposes everything the
management frontend needs: project CRUD, dataset import, run control with
live SSE progress, read-only artifact access, and an environment report.
It drives the same `internal/` packages as the CLI — pipeline semantics,
validation and the event contract (`docs/events.md`) are identical.

```bash
bin/veritmo serve [flags]
```

| Flag | Default | Meaning |
|---|---|---|
| `--addr` | `127.0.0.1:4666` | Listen address. Loopback by default; set explicitly to expose beyond this machine. |
| `--projects-dir` | `projects` | Directory whose subdirectories holding a `scenes.yaml` are the managed projects. |
| `--db` | `.orchestrator/orchestrator.db` | SQLite file for the run history (pure-Go driver, no CGO). |
| `--token` | _(none)_ | Bearer token required on `/api/*`. Also read from `VERITMO_TOKEN` (preferred: flags show up in `ps`). The flag wins. |
| `--cors-origin` | _(none)_ | Origin allowed to call the API cross-origin, e.g. `http://host:4200`. Repeatable, exact match. Default: same-origin only. |
| `--insecure-no-auth` | `false` | Allow a non-loopback `--addr` without a token (prints a warning). |

On startup the server prepends the repo-local `bin/` to `PATH`, so binaries
installed by `scripts/` resolve for preflight, runs and the environment
report alike. `SIGINT`/`SIGTERM` shut down gracefully: an active run is
terminated and recorded as `interrupted`.

## Remote access and authentication

By default the server is loopback-only, unauthenticated and same-origin.
To use it from another machine:

```bash
export VERITMO_TOKEN="$(openssl rand -hex 24)"
bin/veritmo serve --addr 0.0.0.0:4666 --cors-origin http://my-laptop:4200
```

- A non-loopback `--addr` **without a token refuses to start** (exit 2)
  unless `--insecure-no-auth` is given.
- With a token, every `/api/*` request needs `Authorization: Bearer <token>`
  or gets `401` with the usual error shape (`code: "unauthorized"`).
  `GET /api/health` and CORS preflights are exempt.
- CORS: only the listed origins get `Access-Control-Allow-Origin` (never `*`,
  never credentials); `Authorization` and `Content-Type` are allowed.
- **Tickets**: `EventSource`, `<img>`, `<audio>` and `<video>` cannot send
  headers. `POST /api/auth/ticket` (Bearer) returns
  `{"ticket": "...", "expiresAt": "<RFC3339>"}`, valid 10 minutes and for
  nothing else than `?ticket=` on `GET /api/runs/{id}/events`,
  `GET /api/downloads/{id}/events`,
  `GET /api/projects/{id}/artifacts/...`,
  `GET /api/reviews/{id}/findings/{fid}/frame`,
  `GET /api/motions/{id}/preview`,
  `GET /api/music-motion/references/{id}/frames/{name}` and
  `GET /api/music-motion/part-drafts/{id}/preview/{name}`. Tickets are HMAC-signed with a
  per-process secret, so they die on restart. The token itself never goes
  in a URL.
- The token travels in clear over plain HTTP. On untrusted networks use a
  VPN/Tailscale, a TLS reverse proxy, or an SSH tunnel
  (`ssh -L 4666:127.0.0.1:4666 host`, no token or CORS needed).

## Projects

A **project** is a subdirectory of `--projects-dir` containing a
`scenes.yaml`; runs execute with the project directory as working
directory, so each project owns its `tmp/` and `out/`. Project creation
symlinks the repo-level `models/` and `voices/` into the project so the
usual project-relative asset paths work unchanged.

## Error shape

Every API error is JSON with an HTTP status matching the error class
(400/404/409/422 client, 5xx server). Two more are about size and load: `413` when the request body is over the limit of
the endpoint (1 MiB for a JSON message; the endpoints that take uploads, packages or long texts say their own limit), with
nothing written, and `429` when the server refuses more work for now (a full queue, or too many failed authentications from
one address):

```json
{"error": {"code": "validation_failed", "message": "config: scene \"a\" has an empty prompt"}}
```

Codes (the description at `GET /api/openapi.json` lists them all, and a test keeps the two in step): `invalid_request`,
`validation_failed`, `not_found`, `conflict`, `internal_error`, `method_not_allowed`, `unauthorized` (the API token is
missing or wrong), `engine_not_running`, `content_not_allowed`, `unavailable`, `assist_refused`, `describe_refused` (the
error also carries `provider` and `alternatives`: what to retry with), `describe_minor`, `consent_required`, `no_model`,
`model_not_allowed`, `too_many_calls` (the cap of calls to a remote provider), `queue_full` (the queue of runs, downloads or drafts has no room: `429`) and `too_many_attempts` (too many failed authentications from one address: `429` with `Retry-After`).

### API description (`api-documentation`)

| Method & path | Meaning |
|---|---|
| `GET /api/openapi.json` | The OpenAPI 3.0 description of every endpoint in this document (parameters, bodies, responses, the Bearer scheme). It lives under `/api/`, so with a token configured it needs the token like everything else (no exemption, and no public `/swagger` or `/docs` route). The dashboard's **API** page renders it with Swagger UI and sends «Try it out» requests to the connected server with the session's token. The source is `internal/server/openapi.yaml`, embedded in the binary; a test fails when a registered route is missing from it or it lists one that does not exist. The answers of the environment report, the statistics and the resources of a run are described field by field (which fields are always sent and which can be missing or `null`), and a test walks the real answers of those handlers against the description, so a client or a simulated server can be generated from it. |

### Projects (`project-management`)

| Method & path | Meaning |
|---|---|
| `GET /api/projects` | List projects (a query on the database, no folder is read; it can be paged, sorted and searched: `limit`, `offset`, `sort` = `id` (default), `name` or `updated_at`, `q` in the id and the name, with `X-Total-Count` and `Link` in the answer; without them it answers every project in the order of the id): id, declared name, mode, scene count, the `adult` label (`invalid` + `error` when the YAML does not parse). A server starts **censored**: a project marked `adult: true` is not listed and every request that names it, or one of its runs, reviews or files, answers `404` as if it did not exist (`veritmo serve --strict` also hides the projects that were not marked `adult: false`). Creating, importing, duplicating or saving a project with `adult: true` is refused with `422` and the code `content_not_allowed`. Each item says who made it in `client` (the `client:` of its `scenes.yaml`; `embedded` for an ordinary project without one, `unknown` for a project of the generation API without one); `managed=include` lists the projects of the generation API (`api-gen-`, `api-edit-`, `api-vid-`, `api-m3d-`) too, as one more project with its `client` and `kind` (`generation`, `image_edit`, `video_edit` or `model_generation`; absent for an ordinary project; the animations `api-mm-` are never listed), any other value of `managed` is a `400`; `client=a,b` keeps only those clients (names, `embedded` or `unknown`; a name that is none is a `400`). |
| `GET /api/projects/{id}` | One project as the list shows it (`404` for an unknown one). |
| `PATCH /api/projects/{id}` `{name?, client?, adult?}` | Changes the declared name, the client (`null` or `""` removes it) or the adult label (`null` removes it), writing them into the definition as a save does, with its comments and order, and keeping the text it replaces as a version. `400` naming a field that cannot be changed this way, `404`, `409` while the project has a queued or active run, `422` for a value the loader refuses. |
| `GET /api/projects/{id}/versions` · `GET .../versions/{version}` · `POST .../versions/{version}/restore` | The versions of the definition: every save that changes it (`PUT .../config`, a patch, a fix applied by a review or a run, the extension of a clip, a restore) keeps the text it replaces with its date and its `reason` (`save`, `patch`, `fix`, `run`, `extend`, `restore`, `import`); the 20 newest are kept. The list is newest first (`version`, `created_at`, `reason`, `bytes`) and can be paged; the read answers the text in `yaml`; the restore makes it the definition after the validation any save passes (`422` otherwise) and keeps the replaced text as a version. `404` for an unknown version, `409` while the project has a queued or active run. |
| `POST /api/projects` `{"id", "client"?}` | Create a project with a starter `scenes.yaml` that passes validation. `client` (optional, a client name; `422` otherwise) is stored as `client:` in its `scenes.yaml`. `409` if the id exists. |
| `POST /api/projects/{id}/duplicate` `{"new_id"}` | Copy `scenes.yaml` only — `tmp/` and `out/` stay behind. |
| `DELETE /api/projects/{id}` | Delete the project including `tmp/` and `out/`, and its run history (runs, events and resource samples), so it stops counting in the Statistics and the Runs list. `409` while it has a queued or active run. A project of the generation API is not deleted here: `400` naming `DELETE /api/generations/{id}`, `/api/image-edits/{id}` or `/api/video-edits/{id}`. |
| `GET /api/projects/{id}/config` | `{yaml, parsed, valid, warnings, error?}` — raw YAML plus the pipeline loader's structured form. A music project (`output.mode: music`) declares `tracks` and `defaults.music` instead of `scenes`; saving one also checks that its models exist in `models/music/`. A scene may carry its own optional `render` (`{resolution?, steps?, cfg_scale?}`) and `animation` (`{resolution?, frames?, steps?}`) blocks; an absent block or field means the project's value (see [SCENES_YAML.md](SCENES_YAML.md#quality-per-scene)). |
| `PUT /api/projects/{id}/config` `{"yaml"}` | Validate-then-save in the database (the text it replaces is kept as a version). On `422` the definition is untouched and the message is the loader's own (paths and ids outside the rules of [SCENES_YAML.md](SCENES_YAML.md#paths-names-and-limits), a field the configuration does not define, a number above its limit). The body is limited to 1 MB: `413` beyond it, with nothing written. The same limit applies to the `yaml` of the import confirmation, and the text of an import preview is limited to 16 MB. |
| `GET /api/projects/{id}/sources` | `{sources: [{name, kind, size, modified}]}`: the files in the project's `sources/` folder (`kind` is `audio`, `image`, `video`, `blend`, `scene`, `font` or `model`; the audio files are the ones music tracks with a `task` (cover, repaint, extract) transform). A video has `used_by`; a model has `clips`, `triangles` and `needs`. |
| `PUT /api/projects/{id}/sources/{name}?as=picture` | Uploads the **starting picture** of a scene: a picture (`.png`, `.jpg`, `.jpeg`, `.webp`), an animated GIF or a video. A picture is stored as is; a GIF or video is reduced with ffmpeg to its first frame, stored as `<name>.png` (the original is not kept). Answers `201 {name, metadata?}`: `metadata` is present only when the file carried generation settings — `{prompt?, negative_prompt?, seed?, steps?, cfg_scale?, sampler?, model?, width?, height?, strength?}` — read from PNG text chunks (stable-diffusion.cpp / A1111 `parameters`, ComfyUI `prompt`), the `comment`/`description` tags of a video, the comment of a GIF or the EXIF/XMP of a WebP. The reading is bounded (8 MiB inspected, 64 KiB per text value, numbers range-checked) and a file with nothing readable simply has no `metadata`. `409` when the target name exists, `400` for an audio file or an empty body, `422` when ffmpeg cannot read the file, `503` when it is missing and a GIF or video needs it. Without `as=picture` the next row applies. A `.blend` file (a scene for `blender.file`, see `docs/SCENES_YAML.md`) is uploaded here too, stored as is and listed with `kind: blend`. |
| `PUT /api/projects/{id}/sources/{name}` | Uploads a source: raw body, `.mp3` or `.wav` by name (`[A-Za-z0-9._-]`, up to 128 characters), up to 256 MB. A video (`.mp4`, `.mov`, `.mkv`, `.webm`, `.avi`) is converted instead: its audio is extracted with ffmpeg to `<name>.mp3` (the answer gives that name) and the video is not kept; `422` when it has no audio or cannot be read, `503` when ffmpeg is missing. `201 {name}`; `409` when the name exists (never replaced); `400` for a bad name or an empty body; `413` over the limit. Play it with the artifact endpoint (`sources/<name>`). |
| `GET /api/projects/{id}/export?format=dataset\|zip&lang=es\|en` | Downloads the project. `dataset` (default) writes its scenes (video, images) or songs (music) in the format `veritmo import` and the import wizard read: a JSON array of `[id, title, lora_info, full_prompt]` tuples whose `full_prompt` carries the scene text plus the lines `Dialogue:`, `Negative:` (the scene's and the project's), `Motion:` (animate), `Seed:`, `Speed:`, `Silence:` and `Variants:`; an animated graphic is written as `Graphic: <description>` and a title over any scene as `Overlay:`, `Overlay position:`, `Overlay start:` and `Overlay end:` (for songs: `Lyrics:`, `Language:`, `BPM:`, `Duration:`, `Key:`, `Time signature:`, `Seed:`, `Variants:`, `Tags:`). The subject prompt is put in front of every scene, and the style prefix and the voice are folded into each song. What the format cannot carry (the pages written for graphics and titles, models, voice, resolution, animation models, camera and look, own pictures, mixes, favorites, songs made from other songs) comes in the `X-Export-Notes` header (a URL-encoded JSON list); `X-Export-Count` is the number of entries. `zip` downloads the package: `scenes.yaml`, the files of `sources/` and a README, without models or what was generated (`out/`, `tmp/`). `400` for another format, `404` for an unknown project, `422` when there is nothing to put in a dataset. With `zip` the package is the full project: besides `scenes.yaml` and `sources/` it carries the recipe (`RECIPE.md` in the language of `lang`, and `recipe.json`): the settings, the catalog's recommended settings and whether the project follows them, and every file it uses with its catalog entry and URL. Import it with `/api/import/package/preview` and `/confirm`. |
| `GET /api/projects/{id}/loudness?file=` | Integrated loudness (EBU R128) of an audio file of the project, measured with ffmpeg over the whole file: `{lufs}`, null for silence. `file` follows the same rule as `peaks`. Used by the music studio to estimate what normalising a mix does in its preview. `400` for another path or a file that is not audio, `404` when it does not exist, `422` when it cannot be read, `503` without ffmpeg. |
| `GET /api/projects/{id}/peaks?file=&buckets=&bpm=` | Waveform data of an audio file of the project, for the music studio's waveforms (the mixer's timeline, the songs of the results and the repaint range picker): `{duration, buckets, peaks, active, beat_offset}`. With `bpm` (20 to 400) it also looks for the pulse in the first 30 s of the audio and answers `beat_offset`, the second of its first beat (under one beat); it is `null` without `bpm` or when the audio has no clear pulse. `file` is an `.mp3`/`.wav` directly in `sources/` or in a folder of `out/` (`out/<project>/<name>`); `peaks` has `buckets` values from 0 to 1 (the peak level of each equal slice; `buckets` defaults to 800, at most 4000) and `active` is `{start, end}`, the first and last seconds above -45 dBFS (windows of 0.1 s), or `null` when the file is silent. `400` for another path, a file that is not audio, a link that leaves the project or a bad `buckets`; `404` when it does not exist (and for a project the server's content mode hides, like any route of a project); `422` when it cannot be read; `503` without ffmpeg. |
| `POST /api/projects/{id}/transcribe` `{"source", "language"?}` | Reads the lyrics of an `.mp3`, a `.wav` or a kept video of the project's `sources/` with whisper.cpp's `whisper-cli`, on this machine and on the CPU (nothing leaves it): `{language, language_detected, text, segments: [{start, end, text}], dropped, model}`. `language` is an ISO 639-1 code; without it Whisper detects it once at the start and keeps it for the whole file. The previous text is not carried from one window to the next (`-mc 0`) and the voice-activity filter is not used (on a sung line it cut the first seven seconds); empty and note-only segments and every repetition of the same line beyond three in a row are dropped (`dropped` counts them). A source with no words answers `200` with an empty `text`. It is a transcription to review: a sung voice reads worse than a spoken one. Measured here (RTX-less, 8 threads): about 10 s for 30 s of song and about 43 s for 3 minutes; on a song of 3 minutes with known lyrics the word error was 23 % reading it as it is and 22 % from its separated voice. `400` for a bad source, a picture or a language that is not a code, `404`, `409` while a run is queued or active (the model needs memory), `422` when the audio cannot be read, `503` when `whisper-cli` or its model is missing (`bash scripts/get-whisper.sh`), ffmpeg is missing or the memory is short (it says how much), `504` after 10 minutes. |
| `POST /api/projects/{id}/measure` `{"source"}` | Estimates the tempo and the key of an `.mp3`, a `.wav` or a kept video of `sources/`, computed by the server (no model, no GPU, so it does not wait for runs): `{duration, bpm, bpm_alternatives, bpm_confidence, keyscale, key_confidence}`. `bpm` is from 60 to 200 with its half and its double in `bpm_alternatives` when they fall in that range; `keyscale` is written as the music tracks write it (`D minor`); confidences are from 0 to 1. Without a clear pulse `bpm` is `null` and without a clear key `keyscale` is. **They are estimates**: measured on 32 songs generated here with a requested tempo and key, the tempo was right (or at its half or double) in 28 and exactly right in 23, and the key was exact in 23 and the relative key in 3 (the requested value is what the generator was asked for, which it does not always follow); the time signature is not measured. `400`, `404`, `422` (unreadable, or more than 20 minutes) and `503` (no ffmpeg) as for `peaks`. |
| `POST /api/projects/{id}/sources/from-url` `{"url", "name"?}` | Adds the audio of ONE YouTube video as `sources/<name>.mp3`, using `yt-dlp` (install it with `bash scripts/get-ytdlp.sh`; it is optional). The address must be `https` on `youtube.com`, `www.`, `m.`, `music.` or `youtu.be`, never a playlist. No account, cookies or options from the request are used. Limits: 20 minutes of video, 256 MB and 5 minutes of wait; closing the request cancels the download and leaves nothing behind. The default name comes from the title (`[a-z0-9._-]`, up to 60 characters, `-2`, `-3`… when taken); a given `name` must end in `.mp3`. `201 {name}`; `400` for an address that is not a YouTube video or a bad name; `409` when the name exists; `422` when the video needs a sign-in, is unavailable, is a live stream or is too long (with the reason); `503` when `yt-dlp` or ffmpeg is missing; `504` after 5 minutes. Only use material you have the rights to. |
| `POST /api/projects/{id}/sources` `{"from": "out/<project>/<file>", "name"?}` | Copies an exported `.mp3`/`.wav` from `out/` into `sources/` (the original stays). `201 {name}`; `400` when `from` is not an audio file under `out/`; `404` when it does not exist; `409` when the name is taken. |
| `DELETE /api/projects/{id}/sources/{name}` | `204`; `409` while a track of the project names it or a run is active. |
| `GET /api/projects/{id}/cache` | Per-scene/per-phase report of what the next run would do (per track in music mode, with `compose` — `n/a` when the track brings its own lyrics or has a task —, `synth` and `export`): `hit`, `run`, `always`, `n/a`; `cold: true` when no cache manifest exists (e.g. the last run didn't keep `tmp/`). |

### Import (`project-import`)

| Method & path | Meaning |
|---|---|
| `POST /api/import/preview` `{"content", "project"?, "silence_seconds"?, "mode"?, "output_mode"?, "descriptions"?}` | Runs the `veritmo import` mapping on the uploaded JSON/HTML dataset. `mode` is `video` (default, scenes), `motion` (animated graphics: one `motion_graphic` scene per entry, see `docs/IMPORT.md`) `music` (tracks, see `docs/MUSIC_MODE.md`) or `models3d` (the entries of a project of that mode: the prompt of one object plus `Engine:`, `Detail:`, `Variants:`, `Seed:`, `Image:` and `Adult:` lines, see `docs/IMPORT.md`; a censored server refuses `Adult: true` with `content_not_allowed`, `output_mode` does not apply); anything else is a 400 naming the four. Returns `{yaml, warnings, report, entries, imported, silent, instrumental, rejected}`; `warnings` says, for `models3d`, what was changed or ignored (an id made plain, a line that is none of the settings, an `Image:` that has to be in the sources), and, for a video dataset, what is wrong with the 3D scenes (a `Blender:` line whose file is not in `descriptions`, a description no scene names, one that does not pass the checks). `descriptions` is `{"<name>.scene.json": <description>}` (at most 20 files and 1 MB; a name that is not a plain `.scene.json` file name is a `400`). Creates nothing. Placeholders the server can fill (output file, defaults, first available model/voice) come pre-filled so the YAML validates as-is. `output_mode: "images"` (default `video`; not with `mode` music or motion) makes the project an images project (`output.mode: images` in the YAML). |
| `GET /api/library` | The song library: `{songs, ratings, playlists}`, read from the database (no folder is opened, no audio measured). `songs` are the exported songs of every music project (most recent first), each with `key` (`project/track/seed`, the identity favorites use), `project`, `track_id`, `variant`, `seed`, `title`, `caption`, `lyrics`, `bpm`, `keyscale`, `audio_seconds` (the manifest's, rounded), `duration` (the decoded length, to the millisecond, which is the one a music-motion script has to cover; absent without ffmpeg), `file`, `cover` and `favorite`; `ratings` maps a key to 1–5 stars and `playlists` is `[{id, name, songs: [key]}]`. Every song, clip and project carries `client`, and `managed=include` / `client=a,b` work as in `GET /api/projects` (a clip also carries `project_kind` when its project is managed). |
| `PUT /api/library/meta` | Replaces the stars and the playlists (`{ratings, playlists}`; 1–5 stars, up to 200 playlists of 2000 songs, ids of lowercase letters, digits and hyphens) as one change, in the database. A star or a place in a playlist for a key that is not a song of the library is left out; the answer is what was kept. |
| `GET /api/library/songs` | The songs in pages: `limit`, `offset` (`X-Total-Count` and `Link` in the answer), `sort` = `created_at` (default, newest first), `title`, `rating` or `duration`, `q` (title, caption, lyrics), and the filters `project`, `client`, `managed`, `min_rating` (1–5), `favorite=true`, `generator` (`ace-step`, `heartmula` or `diffrhythm2`, the one that made the song; `400` for another value) and `playlist` (in the playlist's order unless `sort` is given; `404` if there is none). The filters combine and `X-Total-Count` counts what they keep. Each song is the item of `GET /api/library` plus `rating`. |
| `GET /api/library/songs/{key}` | One song, or `404`. The key is `project/track/seed` with its slashes sent as `%2F`. |
| `PUT /api/library/songs/{key}/rating` `{"stars"}` | Sets the stars of one song (1–5; `0` removes them) and answers the song. `422` for anything else, `404` for a song that does not exist. |
| `POST /api/library/rescan` | Reads what every project exports again, for audio put or removed by hand: `{added, updated, removed}`. |
| `GET /api/library/playlists` | The playlists in order: `[{id, name, songs}]` (`songs` is how many). |
| `POST /api/library/playlists` `{"id"?, "name", "songs"?}` | Makes a playlist (`201`). The id is made from the name when it is not sent. `409` for an id that exists; `422` for a bad id or name, more than 200 playlists or 2000 songs, or a key that is not a song (named). |
| `GET /api/library/playlists/{id}` | A playlist with its song keys in order, or `404`. |
| `PUT /api/library/playlists/{id}` `{"name", "songs"?}` | Replaces its name and its songs; the same `422` as `POST`. |
| `DELETE /api/library/playlists/{id}` | Deletes it (`204`). |
| `GET /api/storage` | The size of every project (`{projects: [{id, total_bytes, client, kind?}], disk: {free_bytes, total_bytes, warn_below_bytes, low}}`), without following symbolic links, and the free and total space of the disk that holds them. With a media directory (`--media-dir`, see [SERVER.md](SERVER.md)) the answer also has `media: {dir, disk: {free_bytes, total_bytes, warn_below_bytes, low}, projects: [{id, folder}]}`: the absolute path where the projects live, the folder of each one and the free space of that disk, read on every request (a client that writes there can use it to know what is left); without one `media` is absent. `low` is true below `warn_below_bytes` (20 GB, or `VERITMO_MIN_FREE_GB`; `0` disables it); the environment report carries the same `disk`, and launching a run answers `warnings` with the low-space message (it never refuses the run). `managed=include` and `client=a,b` work as in `GET /api/projects`; `disk` is always the disk's, never a sum of the projects, so including the managed ones counts nothing twice. |
| `GET /api/projects/{id}/storage` | What takes the space of one project, part by part: `cache` (`tmp/` without its leftovers), `leftovers` (files of `tmp/` of scenes that no longer exist), `clips` and `animations` (`out/clips/`), `final` (the rest of `out/`), `sources`, `reviews` (`.reviews/`), `backups` (`scenes.yaml.*`), each with `bytes`, `files` and `cleanable`, plus `total_bytes`. |
| `POST /api/projects/{id}/storage/clean` `{"parts": [...]}` | Removes the files of those parts (`cache`, `leftovers`, `clips`, `animations`, `reviews`, `backups`) and answers `{freed_bytes, cleaned}`. `final` and `sources` are `400`; a project with a queued or running run is `409`. |

One run executes at a time per GPU lane (runs without `gpu` share their own
lane); further launches queue FIFO per lane. A run with several GPUs occupies
all its lanes: it starts only when every one is free, and no later run on any
of those GPUs overtakes it while it waits. Run states: `queued`,
`running`, `succeeded`, `failed`, `cancelled`, `interrupted`.

### Event stream (`run-event-streaming`)

| Method & path | Meaning |
|---|---|
| `GET /api/runs/{id}/events` | `text/event-stream`. Full replay of the run's events, then live tail; finished runs replay from history in the same format. |

Three SSE message kinds:

- **default (no `event:` line)** — one pipeline event per message, the
  verbatim JSON object of `docs/events.md`. No fields added, removed or
  renamed; check key presence, not falsiness.
- **`event: run-state`** — server notification: `{id, state,
  queue_position?, artifact?, error?}`. Sent on subscribe and with the
  final state.
- **`event: stream-end`** — explicit end of stream; distinguishes
  completion from a dropped connection. The connection closes after it.

in Ollama that the model occupies 0 bytes of VRAM (otherwise it unloads it and
fails), and always unloads the model when it finishes, so neither VRAM nor RAM
stays held. The model comes from `VERITMO_ASSIST_MODEL` (default
`qwen3:8b`) and the address from the saved setting, else `OLLAMA_HOST` as Ollama
itself reads it (see Settings below).

A request may name another model with `model` (any model installed in Ollama;
nothing is downloaded, an unknown one answers `503` with `ollama pull <model>`;
the memory and CPU-only checks apply to it). `GET /api/assist/models` answers
`{default, models: [{name, size_bytes, fits}]}`: the chat models installed

| Method & path | Meaning |
|---|---|
| `GET /api/providers/presets` | `{presets: [{id, name, base_url, lists_models, text_models, vision_models, key_hint, notes}], models_checked}`: the OpenAI-compatible providers the program knows (`anthropic`, `gemini`, `openrouter`, `openai`, in order of preference); the model names are suggestions checked on `models_checked`. |

| `PUT /api/providers/{id}` | Same body; `key` absent leaves the saved key, `""` removes it (the provider stays), anything else sets it. `404` for an unknown id, `400` for the built-in one (change its address in the Ollama setting). |
| `GET /api/providers/{id}` | One provider as the list shows it (the built-in `ollama` too), with `key_set` and never the key; `404` for an unknown id. |
| `DELETE /api/providers/{id}` | Removes the provider, **its key** and the acknowledgement of its address (`204`); `409` naming the task while one is routed to it. |
| `POST /api/providers/{id}/test` | Sends one short chat (`Reply with OK`, up to 512 tokens so that a model that thinks first can answer, 10 s) to an `openai` provider's text model and, when `lists_models` is true, lists its models (5 s; an Ollama is tested by its tags): `200 {ok, host, remote, chat_ms?, models?: [{name, vision?}], models_note?, error?}`. `ok` means the chat answered with content; a provider that does not list models gets `models_note`, not a failure. **Keys.** They live only in `~/.config/veritmo/keys.json` (mode 600, in a directory of mode 700, next to the token): never in `settings.json`, `scenes.yaml`, an exported package, the environment report, a log line, an error message or an API answer. A key of at most 500 characters with no spaces is accepted. **A key is never sent over plain `http` to another machine**: such a provider is refused (`400`, "use an https address") when it is saved or tested with a key; `http` to `localhost`/`127.0.0.1` is allowed (a local vLLM or LM Studio). The server follows no redirects when it talks to a provider, so a key cannot be sent to an address you did not choose.

Which provider runs each task is chosen under Routing below.

### Routing tasks to providers (`provider-routing`)

| Method & path | Meaning |
|---|---|
| `GET /api/routing` | `{routing: {assistant, describe_image, describe_video, quality, motion_graphics}, max_calls}`; each task is `{provider, name, remote, consented, model}`. The tasks are the prompt assistant (picture, movement, song and videoclip-storyboard prompts), describing a picture, describing a clip (one scene or one per shot), the clip quality check and writing the HTML page of a motion graphic or overlay. **Every task defaults to the built-in Ollama**, so nothing changes until a provider is chosen. `model` is the provider's text model for `assistant` and `motion_graphics` and its vision model for the other three (empty for an Ollama that declares none: it picks among its installed models). `remote` says the provider is not this machine; `consented` that the user accepted sending data to its current address. When a saved provider made from a preset has been tested with success, `suggested: {motion_graphics, quality}` names it (`{provider_id, name, reason}`; the first by the presets' order; absent otherwise): a hint a dashboard can offer in one click, never applied by itself. |
| `PUT /api/routing` `{routing?: {task: provider id}, acknowledge_remote?, max_calls?}` | Routes tasks (`ollama` puts a task back on the built-in one). Routing to a **remote** provider needs the user's acknowledgement that the pictures, clips or texts of that task leave this computer: send `acknowledge_remote: true` (after showing them the consent dialog) or call `POST /api/providers/{id}/acknowledge` first; without it `400 consent_required` naming the provider and what is sent. An OpenAI-compatible provider without the model the task needs is refused (`400 no_model`). Nothing is saved if anything fails. `max_calls` (at least 1, default 60) is the most calls one job may make to a remote provider. |
| `POST /api/providers/{id}/acknowledge` | Records the acknowledgement for the provider **at its current address**; editing the address makes it stop counting (it is checked every time the provider is used, not only when routing is saved). `404` for the built-in provider, which needs none. |

`POST /api/assist` and `POST /api/describe` (and the videoclip plan with `ai`) take an optional `provider` that replaces the routing **for that one call** (with the same consent rule if it is remote). `describe` answers also carry the `provider` used, and a scene made from it records `described_by` as the model alone for the built-in Ollama and `provider-id:model` for any other. **Nothing retries or switches provider by itself**: a provider that fails, refuses or slows down is reported and that is all.

A job that would make more calls to a remote provider than `max_calls` is refused before any call (`400 too_many_calls`, with both numbers): a picture is 2 calls (age check and description), a clip as one scene 2 per frame plus 1, one scene per shot up to 3 per shot. A local provider has no cap. A model that cannot read pictures (a typical 400 from the provider) answers with a message that says so. The age check, refusals, the deletion of refused files and the minors rule are the same with any provider. The Ollama-only behaviour (CPU only, the memory and installed-model checks, VRAM verification, unload) applies only to Ollama providers, and only a model that loads into **this** machine's memory waits for a run in progress.

### Generation: a video or a picture edit in one call (`video-generation-api`, `image-edit-api`)

A client that only wants "make a video from this prompt and picture" or "retouch this picture" does not need the flow of projects, sources, YAML and runs. The server plans it (engine, models, resolution for an aspect ratio and a quality, the length of the scene, audio), creates it as a **project of its own**, launches its run on the normal queue and answers at once. A generation or an edit is a project named `api-gen-…` or `api-edit-…` (these prefixes are reserved: `POST /api/projects` refuses them); it is left out of `GET /api/projects`, the storage per project, the library, the kept clips and the statistics by project. Its run is a normal run: follow it with `GET /api/runs/{run_id}/events`.

| Method & path | Meaning |
|---|---|
| `GET /api/generation/options` | `{video, image_models, aspect_ratios, qualities}`. `video` lists the eleven ways of making a video in a stable order (`h3-full`, `wan-high`, `ltx`, `h3-draft`, `wan-medium`, `wan-low`, `ad-high`, `ad-medium`, `ad-low`, then the two of the references, `h3-ref` and `h3-ref-draft`, which are after the others so the default does not change): `{id, name, description, engine, available, reason?, clip_seconds, duration: {min, max, default}, audio, estimate?, default, inputs}`. `inputs` says what the option takes besides the prompt: `{start_image, end_image, reference_images?, reference_videos?, reference_audios?, scene?}` where the references are `{min?, max, max_seconds?}`; what is missing is not accepted. `h3-full`, `h3-draft` (when the first/last-frame bundle is the one in use) and `ltx` take `end_image`; Wan and AnimateDiff take the start picture alone; `h3-ref` and `h3-ref-draft` (MiniMax H3 with its references bundle, always at 768x416) take references and neither a start nor a last picture. After them comes `blender` (a 3D scene that Blender draws from a description sent with the request: `inputs: {scene: true}`, duration from 1 to 30 s, never the default; `available: false` with the `reason` and how to install it when Blender is not usable). The reference limits are the ones measured for the card the server would use: 2 pictures, 1 video of at most 2 s and 1 audio of at most 3 s with 12 GB, and 6 pictures, 2 videos of at most 3 s and 3 audios of at most 4 s with 16 GB. An option this machine cannot run has `available: false` and the `reason` (not installed, or what it needs); the first available one is the `default`. `clip_seconds` is how long the clip the engine makes by itself lasts (played forward and back, or once when the model writes the sound); `estimate` is the seconds a generation takes at the best quality, 16:9 and with no start picture, on this machine (from the catalog timings and the card's measured speed); it does not grow with the duration. `image_models` lists the models a picture can be retouched with, the editing models first: `{id, name, description, kind: "img2img"\|"instruction", available, reason?, strength, negative_prompt, max_variants, default}`. A server that hides adult content does not list the models made for adults (nor in `GET /api/assets/catalog`) and refuses one by name as unknown; one that shows everything lists them and labels what they make `adult`. |
| `POST /api/generations` | `{prompt?, option?, duration?, aspect_ratio?, quality?, audio?, adult?, client?, blender?}` as JSON, or `multipart/form-data` with the JSON in a `request` part and the start picture in an `image` part (png, jpg, jpeg or webp). A prompt or a picture is needed (with a picture the prompt describes the movement). Parts for the options that announce them in `inputs`: `end_image` (one picture the clip ends on; it needs `image`; the clip then plays once, forward, and holds its last frame to fill the duration) and the repeated `reference_images`, `reference_videos` (mp4, mov, webm or mkv) and `reference_audios` (mp3, wav, m4a, aac, ogg or flac), in the order they come: at least one reference picture is needed (it anchors the scene and is the first reference, named `<Picture 1>` in the prompt, the next ones `<Picture 2>`…), the references cannot be combined with `image` or `end_image`, and the counts and durations are those of `inputs`. `reuse_inputs_of: <id>` uses the files of another generation (its start and last picture, its references) without sending them again; it is refused together with input parts, for an unknown generation or one that kept none. With `option: "blender"` the video is a **3D scene**: `blender: {description}` is the JSON of a scene (see the writer and the preview with no project, `POST /api/blender/descriptions` and `/preview`), no prompt is needed and no picture or reference is accepted; the description is checked like a hand-written one for the request's `duration` (keys in seconds, no design, no tempo, no font files; `422` naming each fault by its place in the JSON, nothing created), stored in the project's `sources/` as `<id>.scene.json` and reported in `inputs` as `{kind: "scene", name, address}` (the `address` answers the JSON with the access of the video), `aspect_ratio` gives the frame and `quality` the size and the samples; the `request` a generation reports has `blender: {}`. `reuse_inputs_of` of such a generation copies its scene (`422` for another option), and a `blender.description` sent with it wins over the reused one. Every refusal is `422` with the part and what is accepted. Defaults: the default option, 5 s, `16:9`, quality `high` (`draft`, `normal` and `high` scale the sides of the picture and of the clip by ½, ¾ and 1), no audio. `duration` is the length of the **scene**; the engine's clip is short (`clip_seconds`) and is stretched and looped to fill it, clips are never chained. `adult` is the label the client puts on the generation (the same as `adult` in a scenes.yaml; `true` is refused by a server that hides adult content). `client` is the name of the dashboard that asks, written by that dashboard itself (for example `video-studio`): one to 32 lowercase letters, digits or hyphens (`^[a-z0-9-]{1,32}$`); without it the client is `unknown`. It is stored in the `scenes.yaml` of the generation's project (`client:`) and in its run, and groups the statistics (`client=`, `by_client`) and the metrics; it is a label, not a credential. Answers `202 {id, state, progress, request, client, run_id, clip_seconds, estimate, created_at}`. `422` with the reason when the option does not accept it (no prompt and no picture, unknown option, duration outside `duration`, an aspect ratio or quality that is not offered, audio on an option that cannot write it, adult content on a server that does not keep it, a `client` that does not fit the form), `503` (`unavailable`) when the option cannot run now; nothing is created in either case. |
| `GET /api/generations` · `GET /api/generations/{id}` | The generations, newest first, and one of them: `{id, state: "queued"\|"running"\|"done"\|"failed", progress (0 to 100, from the phases of the run that have ended), request, client (`unknown` for one made before the field), run_id, clip_seconds, estimate?, created_at, inputs, video?, error?}`. `inputs` lists the files the generation used, in order, each `{kind: "start_image"\|"end_image"\|"reference_image"\|"reference_video"\|"reference_audio", name, address}` with the address it is served from, read-only (an empty list when it used none; a generation made before this field shows its start picture alone). When `done`, `video` is the address of the video, an artifact served read-only with the access the rest of the API asks for; when `failed`, `error` says why (`cancelled` and `interrupted` count as failed). `404` for an unknown one. |
| `DELETE /api/generations/{id}` | Cancels the run when it is queued or running and removes the generation with its files and run history. `204`; `404`; `409` if the run does not stop. |
| `POST /api/image-edits` | `multipart/form-data`: a `request` part `{model?, prompt, negative_prompt?, strength?, variants?, adult?, client?}` (`client` as in `POST /api/generations`) and the `image` to edit. `img2img` models start from the picture with a `strength` (above 0, at most 1; default 0.6) and make up to `max_variants` (8) pictures; `instruction` models (FLUX.1 Kontext, Qwen-Image-Edit) change the picture by the prompt, at the shape of the picture, make one, and refuse `strength` and `negative_prompt`. Defaults: the default model, 1 variant. Answers `202` with the same shape as a generation plus `results`; `422` for a blank prompt, a missing picture, a setting the model does not take or one outside its limits, `503` when the model cannot run now; nothing is created in either case. |
| `GET /api/image-edits` | The picture edits, newest first, each as `GET /api/image-edits/{id}` answers it. Like `GET /api/generations` and `GET /api/video-edits` it can be paged (`limit`, `offset`, `sort=created_at`; `X-Total-Count` and `Link`) and kept to some clients (`client=a,b`); without parameters it answers every one. `400` for a value that is not valid. |
| `GET /api/image-edits/{id}` · `DELETE /api/image-edits/{id}` | `{id, state, progress, request, client, run_id, created_at, size_bytes, results?, error?}` with, when `done`, one result per variant `{variant (from 1), seed, image}`: the seed that makes it again (from the manifest of the run) and the address of the picture. `DELETE` cancels and removes it like a generation. |

### Video editing: a video you already have, in one call (`video-edit-api`, `video-edit-motion-library`)

The guide to all of this, with the measured times and what each tool needs, is [VIDEO_EDIT.md](VIDEO_EDIT.md). `remove-background` and `depth` (grey frames, near white and far black, on one scale for the whole clip, without sound) work while the `videovision` service runs (`remove-background` gives an MP4 on a plain colour, or a WebM with alpha; a video with nobody in it ends `done` with a note and comes out unchanged). `scale`, `interpolate` and `reframe` work with ffmpeg alone (`scale` with `engine: quality` uses Real-ESRGAN and `interpolate` uses RIFE when `scripts/get-upscalers.sh` has installed them, on any card with Vulkan; without them, or if they fail or the frames would not fit the disk, the lanczos and `minterpolate` filters are used and the result's `notes` say why; the options' `notes` say what is not installed); `extend` makes the video longer with a new clip that starts at its last frame (a generation with a start picture, made with MiniMax H3 or LTX, whichever `engine` names or the first that can run; the prompt is required) and joins the two without showing the last frame twice, at the source's size and rate and without sound. One clip is what the engine makes by itself (about 2 s on this machine), so asking for more gives that length and a note says so; the result says how many times the video has been extended (kept in the file's comment tag, so it survives being sent back) and warns that the quality drops with each time. Measured on an RTX 4070: H3 about 290 s, LTX about 145 s. **The library of motions** (`/api/motions`, empty until you add some; the server ships no videos): `GET /api/motions` lists them (an empty list, newest first; `{id, title, tags, duration, people, state, preview, error?}`), `GET /api/motions/{id}` gives one and `GET /api/motions/{id}/preview` its small preview video (`video/mp4`). `POST /api/motions` takes `multipart/form-data` with a `request` part `{title?, tags?}` and the `video` part (or JSON with `source`, the address of a YouTube video, which is downloaded in the background), answers `202` with the state `processing` and prepares it in the background: the control of the whole video (the depth of the people, black elsewhere, three-channel PNG at 16 per second, in the shape of the video: 832x480, 480x832 or 640x640) and the preview; the state ends `ready` (with `duration` and `people`, an estimate: people who touch count as one) or `failed` with the reason. The video is looked at when the request arrives: `422` if it is not a video, lasts more than 30 seconds or less than 2.1, or nobody is in it, `503` if the vision service is not running; nothing is kept in those cases, and the video itself and its frames are never kept. `DELETE` stops the preparation if it runs and removes the files (`204`). The library is in the settings folder (`motions/`).

`motion-control` moves the movement of the people of a video, or of a motion of the library (`motion` in the `request`, instead of the `video` part: its control is already made, so the request is accepted at once and the vision service does nothing; `start` picks the window of 33 frames inside it, `422` if the motion is unknown, not `ready`, or lasts less than `start` plus 2.1 s), onto the people of a reference picture (the `image` part): 33 frames at 16 per second (about 2 s), from `start` seconds into the video, in the shape of the picture (832x480, 480x832 or 640x640) and with the picture's background, not the video's. The control (the depth of the people, the rest black) is made by the vision service when the request is accepted, which refuses with `422` if nobody is in those 33 frames or the video is shorter than them, and is kept for the run; then `sd` runs Wan 2.1 VACE 1.3B (`prompt`, `strength` 0.2 to 1, default 0.6, and `guidance` 1 to 10, default 6, the cfg scale of `sd`: lower, about 4, burns the highlights less (on the same pictures from 36 % to 21 % of the pixels for a person, from 24 % to 14 % for two cats) but follows the prompt less, and the cats came out half human). It takes about 330 s on an RTX 5060 Ti and 5.5 GB of video memory, has no sound, and is **soft and made for subjects with a human outline**: the people of the picture do not keep their identity well and the result can look washed out or invented (see the options' `notes`). The prompt matters more than the strength: describe the people and the place as the picture shows them, with natural lighting; on the same request, «a woman with red curly hair and a cream sweater dances in a **bright** kitchen» came out burnt white with invented legs and the same without «bright», in natural light, kept the hair, the sweater, the jeans and the pose. It needs `sd`, the three model files (`wan2.1_vace_1.3B_fp16.safetensors`, `wan_2.1_vae.safetensors`, `umt5-xxl-encoder-Q8_0.gguf`, in `models/video/`; the catalog has them as one entry, **Wan 2.1 VACE 1.3B** (kind `video`, 10.6 GB, the VAE and the text encoder shared with the Wan bundles, not offered as a generation option)), the vision service and a card with 6 GB, and says which is missing. Every tool is listed with `available: false` and the reason when it cannot run now (those that read a picture with a network need the `videovision` service, started from the Environment screen, and say when it is stopped, not installed or lacks a model file) (the change `add-video-editing-tools` adds them one by one). `interpolate` drops the sound; `reframe` by `crop` follows the people (the box of the person mask at 4 samples per second, smoothed over about a second) while the `videovision` service runs, and is centred, with a note saying why, when it does not run or nobody is found; by `pad` makes the smallest canvas of the ratio that holds the whole picture, by `crop` the largest window that fits, centred. A client that has a video can scale it, raise its frame rate, reframe it, cut the people out, get its depth, make it longer or move the motion of some people onto another picture, with one request and no projects, sources or YAML. Edits are hidden projects like the generations and the picture edits (`api-vid-…`), do not appear in `GET /api/projects`, the storage or the statistics per project, and go through the same run queue (one heavy process at a time, with the same notice).

A tool that lacks a file, a binary, the vision service or card memory is listed with `available: false` and the `reason`; the call never fails. |

### Assets and downloads (`model-management`)

The built-in catalog (`GET /api/assets/catalog`) includes two image bundles for
`defaults.model_set`: `krea2-turbo-q4` and `krea2-intorealism-v4-fp8`. Each is a
`model` entry with three files carrying a `role` (`model`, `text_encoder`,
`vae`); it counts as installed only when all three exist, and installing it
downloads only the missing ones, so the text encoder and the VAE that the two
share are fetched once. An entry whose files need an account key carries

Managed kinds and their directories (relative to the server's working
directory): `model` → `models/` (`.safetensors`, `.ckpt`, `.gguf`), `voice`
→ `voices/` (`.onnx`, `.onnx.json`), `lora` → `models/loras/` (same
extensions as models) and `video` → `models/video/` (`.safetensors`,
`.gguf`) `adapter` → `models/music/adapters/` (music LoRAs: each is one `.safetensors` file or a folder with `adapter_model.safetensors` and `adapter_config.json`, listed and deleted as one unit; a download may name a file `<folder>/<file>`, one level), and `music` → `models/music/` (`.gguf`: the language model, text encoder, synthesis model and VAE of the music engine, kept flat because the engine finds them by name). LoRA files are stored and listed only — the pipeline
does not apply LoRAs yet (the `lora` kind carries a `note` saying so); the
`video` files are the animation models (Wan, or the AnimateDiff motion module)
that a project's `defaults.animate` uses, and its `note` says so. Files under `models/video/` never appear in the
`model` listing (they are listed in the `music` field of `GET /api/environment`).

| Method & path | Meaning |
|---|---|
| `GET /api/assets` | `{kinds: [{kind, dir, extensions, note?, assets: [{name, size}]}]}`. `.partial` and hidden files are never listed; a missing directory is an empty list. |
| `GET /api/assets/catalog` | `{entries: [{id, kind, name, description, starter?, size_bytes, vram_mb?, min_ram_gb?, preset?, prompt_hint?, styles?, style_rank?, quality?, files: [{name, role?, url}], installed}]}` — the built-in recommended list. `description` says what the asset is for; `vram_mb` (models only) is a rough minimum GPU memory estimate, not a measurement (SD 1.5, SDXL base, Piper voices with their `.onnx.json`). `timing` (`{seconds, resolution, steps, frames?, turbo_seconds?, turbo_steps?, measured}`, image models and video bundles) is how long one picture or clip takes on the reference machine (an RTX 5060 Ti with 16 GB), which the dashboard scales to the project and the GPU to estimate a run; `measured` says whether it was timed or is an estimate. `starter` flags a sensible first install; `preset` (`{steps?, cfg_scale?, resolution?}`, on Krea 2 Turbo, IntoRealism, Juggernaut XL, Pony and the AnimateDiff module) holds the settings measured to work with the model — a missing field means no recommendation, and `cfg_scale: 0` is a real value; `prompt_hint` (only Pony) is advice about the prompt the model needs, for display: the server never changes a prompt with it; `styles` (`photo`, `anime`, `general`) and `style_rank` (lower is preferred) say what an image model is for, and `quality` (`low`, `medium`, `high`) places a Wan bundle on the editor's quality scale; the editor uses them to choose among the installed models, and they are omitted when not declared; `role` (`model`, `text_encoder`, `vae` for Wan video bundles, `high_noise_model` too for A14B, and `motion_module` alone for the AnimateDiff entry, whose SD 1.5 checkpoint is the one already installed under `model`; `lm`, `text_encoder`, `dit`, `vae` for `music` bundles) names each file of a bundle; `installed` is true when every file is on disk. Starting a download from a catalog `id` fetches only the files that are missing (bundles share e.g. the VAE) and answers `409` when all are already there. |
| `PUT /api/tokens/{service}` `{"token": "<key>"}` | Save the download key of `huggingface` to the standard Hugging Face token file; each is written atomically with permissions `0600` (directory `0700` if created), and takes effect on the next download without a restart. A symbolic link at the destination is refused. `204`; `400` unknown service, malformed body or a key that is not 8–512 printable ASCII characters without spaces (checked for shape only, never against the remote service); `500` when the file cannot be written (the previous key is kept). The key and the file path never appear in any answer. There is no operation that returns a key. |

Removing the Hugging Face key also removes it for other Hugging Face tools that share that file. |
| `DELETE /api/assets/{kind}/{name}` | `204`. Removes a voice's companion `.onnx.json` too. `404` unknown kind/file, `400` invalid name, `409` while any run is queued or active. |
| `POST /api/downloads` `{"kind"?, "url"? \| "repo"?, "file"?, "revision"?, "id"?, "name"?, "overwrite"?}` | Queue a download: a direct `http(s)` `url`; a Hugging Face `repo` + `file` (+ `revision`, default `main`); or a catalog `id`. `name` overrides the file name (default: base of the URL path / `file`). Downloads run one at a time. Each file is written to `<name>.partial` and
renamed only after the whole job (all files of a voice) arrived complete,
so an asset is never half installed. The server refuses to connect to
loopback, private, link-local or carrier-grade-NAT addresses (checked at
connection time, so redirects are covered), follows at most 10 redirects,
and fails early when the announced size exceeds the free disk space. The Hugging Face key comes from `HF_TOKEN` or, when that is empty, from the standard Hugging Face token file (`$HF_HOME/token`, else `$XDG_CACHE_HOME/huggingface/token`, else `~/.cache/huggingface/token`), read on every download; it can be saved from the API (below). It is
sent only to `huggingface.co` hosts. When Hugging Face refuses a download
with 401/403 (private, gated or non-existent repo — it answers 401 for all
three) the download fails with a message that lists the steps: accept the
license on the model page, create a read token (Settings → Access Tokens)
and save it in the Models tab (or in `HF_TOKEN`); if a token is already set, it
says that token's account has no access. The token value is never included.


## Front end

The binary has no front end inside and `go build ./...` needs no Node/npm toolchain. A built front end is served from a
folder with `veritmo serve --web-dir <folder>` (or `VERITMO_WEB_DIR`): its files at `/`, `index.html` for the
paths that are not files and not under `/api/`, hashed files cached for good and the rest revalidated. Without it `/`
answers a plain-text note that the server has no front end. See
[SERVER.md](SERVER.md#a-front-end-from-a-folder---web-dir).

## Verified examples

With `bin/veritmo serve` running from the repo root:

```bash
curl -s http://127.0.0.1:4666/api/health
# {"status":"ok"}

curl -s -X POST http://127.0.0.1:4666/api/projects -d '{"id":"demo"}'
# {"id":"demo"}

curl -s http://127.0.0.1:4666/api/projects
# [{"id":"demo","name":"demo","mode":"video","scene_count":1}]  (music projects: "mode":"music" and "track_count")

curl -s http://127.0.0.1:4666/api/projects/demo/cache
# {"mode":"video","cold":true,"scenes":[...]}

curl -s http://127.0.0.1:4666/api/environment | head -c 200
# {"binaries":[{"name":"piper",...}],...}

curl -s -X POST http://127.0.0.1:4666/api/downloads \
  -d '{"kind":"model","url":"https://example.com/tiny.safetensors"}'
# {"download":{"id":"dl-...","state":"queued","kind":"model","name":"tiny.safetensors",...}}

curl -sN http://127.0.0.1:4666/api/downloads/<id>/events
# event: download-state ... event: progress ... event: stream-end

curl -s -X DELETE http://127.0.0.1:4666/api/assets/model/tiny.safetensors -w '%{http_code}\n'
# 204
```

Launching runs additionally requires the pipeline binaries (see
[INSTALL.md](INSTALL.md)); the launch endpoint refuses with the preflight error otherwise.
