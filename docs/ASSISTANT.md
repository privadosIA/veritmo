# Prompt assistant

[← Back to the README](../README.md)

This page covers four things that use a local or remote language model: the [prompt assistant](#prompt-assistant), [songs: style, tags and lyrics for each generator](#songs-style-tags-and-lyrics-for-each-generator), [describing a picture or a clip](#describing-a-picture-or-a-clip) to get a prompt from a reference, and [other providers](#other-providers) (another Ollama, or any OpenAI-compatible server) for any of them.


`veritmo assist <image|motion|music> "<text>"` writes a prompt in English from a scene (or song) description in any language and prints only the result, so it works over SSH:

```bash
bin/veritmo assist image "Una mujer lee un libro en una cafetería soleada por la mañana"
bin/veritmo assist motion "una mujer lee un libro en una cafetería"
bin/veritmo assist music "Una balada triste sobre volver a casa una noche de lluvia, con piano"
```

`image` gives one photographic prompt (~70-100 words: subject, setting, light, camera, mood) for Krea 2 or SDXL; `motion` gives ≤25 words of subtle scene and camera movement for an `animate: true` scene; `music` gives a `STYLE:` line (English) and `LYRICS:` with `[Verse]`/`[Chorus]` tags in the language of your description (`--instrumental` for the style only). The same is available to the server as `POST /api/assist` (see `docs/http-api.md`), which also has a `tags` task: the music studio uses it, when the HeartMuLa generator is chosen, to write the style tags of a track (4 to 8 short English words separated by commas) from its style text. With a `generator` (`heartmula` or `diffrhythm2`) the `music` task also writes the tags and the structure tags those engines read (`[intro]`, `[verse]`, `[chorus]`, `[outro]`, `[inst]`, `[solo]`… in lower case), so applying the proposal leaves the track ready to create. A fourth task, `lyrics-from-transcript`, puts the transcription of a song (read from an audio or a video by Whisper, see the music mode) into sections and proposes its style and tags: it keeps the words as they were heard (the server checks that the answer has no word the transcription lacks, and otherwise keeps the transcription as it was), and drops from the style and the tags any instrument that neither you nor the picture mentioned.

It uses a local [Ollama](https://ollama.com) model and **never touches the GPUs**: each request forces the CPU (`num_gpu: 0`), checks in Ollama that the model has 0 bytes of VRAM (otherwise it unloads it and fails), and unloads the model as soon as it finishes so no VRAM or RAM stays held. If another client had left the model in a GPU, the first call moves it to the CPU and frees that VRAM; while Ollama starts its CPU process it may probe the GPUs for under a second (about 150 MB per GPU, measured), which is Ollama's own device discovery, not the model. Install the default model once with `ollama pull qwen3:8b` (~5 GB; it is never downloaded automatically) or choose another with `--model` or `VERITMO_ASSIST_MODEL`; point at a different Ollama from the **Settings** screen (saved, applied without a restart, and read by the terminal commands too) or with `OLLAMA_HOST`; with an Ollama on another machine the text and the pictures of every request travel to it, and the screen says so. **If the model refuses** (it happens with adult descriptions: Qwen3 and most models are trained to), the editor and the music studio say that the model refused; the refusal comes from the model, the application adds no content filter and its instructions say nothing about content.  On the CPU it writes ~8 tokens/s: a prompt takes 5-10 s (a few seconds more the first time, while the model loads). Models under ~8B do not follow the task well and models over ~14B are too slow on the CPU. It needs the model size × 1.3 + 4 GiB of free RAM and refuses to run otherwise; the server also refuses (`409`) while a pipeline run is queued or active.


## Songs: style, tags and lyrics for each generator

The `music` task (`veritmo assist music`, `POST /api/assist` and, from the Create page, `POST /api/assist/request`) writes for the generator that will make the song, because each reads different words:

| Generator | Style | Lyrics |
|---|---|---|
| ACE-Step (default) | `STYLE:` one English sentence of 20 to 40 words | any language; `[Verse]`, `[Chorus]`, `[Bridge]`, `[Outro]` |
| HeartMuLa | `TAGS:` 4 to 8 English tags **chosen only from the vocabulary** (below) | any language; lower-case `[verse]`, `[chorus]`, `[bridge]`, `[outro]` (also `[intro]`, `[inst]`, `[solo]`, `[hook]`, `[break]`, `[end]`) |
| DiffRhythm2 | `TAGS:` short English words, written as a sentence for the model | **English only**; the same tags as HeartMuLa; no instrumental songs |

**The vocabulary.** The tags of HeartMuLa come from `internal/assistant/assist/tagvocab.go`: 109 tags in seven categories (genre, mood, instrument, tempo, vocal, era and production), spelled as the public dictionary of the model spells them (`hip-hop`, `lo-fi`, `r&b`, `synth`), and ten popular combinations (Chill Lo-fi, Epic Cinematic, Upbeat Pop, Dark Electronic, Acoustic Ballad, Retro Synthwave, Jazz Cafe, Hip-Hop Beat, Rock Anthem, Ambient Meditation). The model is told the list and the combinations as examples, and the server checks its answer: lower case, synonyms mapped to the dictionary's spelling (`hiphop`, `synthesizer`, `medium tempo`…), tags outside the list and repeated ones dropped, the genre first, at most two genres, two moods, three instruments, one era and one speed word, and eight tags in all; a suggestion with no genre carries a warning. The list is a starting point taken from public descriptions of the model, not an official one: HeartMuLa reads tags as free text and answers better to the kinds it was trained on, so changing the table is a one-file edit, and whether a change improves the songs is checked by listening. `GET /api/assist/music-tags` serves the same list and combinations to the dashboard.

**The lyrics follow the length of the song.** Stanzas of four lines with the chorus repeated word for word: up to 75 s verse, chorus, verse, chorus and outro (about 16 lines); normal length adds a bridge and the chorus a third time (about 28 lines); over 150 s there are three verses (about 36). A caller gives the length in `seconds`; without it the song is normal. A very long or dense text can make the generator skip a verse, hence the cap.

**Listening to a song.** `POST /api/assist/listen` takes a recording of a song that is playing (the Create page's ear button) and answers what kind of song it is: its tempo and key (an estimator of our own, only when clear), its language, whether it has words, how it sounds (measured on the recording: timbre, bass, texture, dynamics, density of the rhythm, loudness), a style description and what it is about, and a sentence that asks for a new original song of that kind. Whisper reads a few words of the lyrics on this machine; **the lyrics heard and the recording are never returned, kept or logged**. The genre is the assistant's best guess from those words and the figures (there is no audio classifier), so it can be wrong with noise or without words; when it cannot tell it says "unknown genre" and the card asks you to check the style. A recording with almost no recognised words is not declared instrumental: the voice may simply not have been readable. See `docs/http-api.md`.

**Every prompt for a generator is in English.** The assistant writes the image prompt (70 to 100 words), the movement prompt, the style of a song and the shots of a music video in English whatever language the request is in; only the lyrics and the words a video says keep the user's language. A picture that someone attaches to an image request has no scene to describe, so the request ("ponle el pelo rubio al chico de la izquierda") becomes a short imperative English **instruction** for the editing models: it says who by where they are in the picture, avoids naming other colours (naming the red shirt made a model dye the hair red), describes only the change and ends with "Keep everything else exactly the same." (added by the server). When the assistant is not available, the words go as the user wrote them.

## Drawing an SVG

`POST /api/assist/svg` writes one SVG from a description, with the same guards as the other tasks (the routing of the task, the wait for a run in progress, the memory rule, CPU only, the model's own refusal). It is not a task of `POST /api/assist` because its answer is a document, not a line. The prompt asks for a single `<svg>` with a `viewBox`, an `id` on every element worth selecting or animating, fills and strokes as attributes and no text, style block, gradient, filter, script or outside reference, at most 40 elements. The server checks the answer cheaply (it parses as XML, the root is `<svg>`, it has a `viewBox`, no `<script>`, `<foreignObject>`, event attribute or outside reference) and answers `422` otherwise; it does not judge whether the drawing is any good, which depends on the model: a small one writes a plain shape or one big path, and a bigger model (within the memory rule) draws better. The catalog of the music mode lists `svg` in its `features` so a client knows the operation exists.

## Planning a whole video from one sentence

`POST /api/assist/plan {text, generator?, language?, seconds?, examples?, model?, provider?}` turns one sentence, in any language, into the plan of a music video: the song's brief (title, caption, lyrics, tags, length, written by the `music` task for the generator), the animation's choices (`style`, `level`, `fps`, `mode`, a one-sentence `concept`; only values the catalog of `GET /api/music-motion/catalog` offers, an empty one comes with a warning) and up to six parts, checked against the catalog (a part that does not exist carries the `request` that asks for its draft). `animation.prompt` is the sentence itself, to use as the direction of the piece. It has the guards of the other tasks (routing and consent, the wait for a run in progress, the memory rule, CPU only, the model's refusal: `422 assist_refused` only when nothing could be written) and makes two assistant calls. A server with it lists `plan` in the `features` of the catalog. `provider` replaces the routing for that call only, as in the other calls.

## A whole dataset from one sentence

`POST /api/assist/dataset {mode, text, language?, engine?, negative?, look?, images?: {variants}, generator?, picture?, project?, examples?, model?, provider?}` writes several entries in the tuple shape `POST /api/import/preview` reads (`[id, title, lora_info, text]`): the scenes of a storyboard (`mode: video`), animated graphics (`motion`: a part of the catalog with its `Param` lines, or a described graphic) or songs (`music`: a style, `Lyrics:` and the `generator`'s `Tags:`, one more model call per track, at most 6) or 3D models (`models3d`, below). At most 12 entries. The model writes only what is its job (the narration, the movement, the picture line, the brief of a song); the lines the request fixes are written by the server (`Negative:`, `Variants:`, the `look` at the end of each picture line), and every entry goes through the import's own mapping before it is returned, so what comes back previews and an entry that fails is left out with a warning. It has the guards of the plan. With `picture: "blender"` (video mode) every scene is a 3D scene: the server writes the description of each with the writer and checks of `blender/descriptions` (up to 3 attempts), writes a `Blender: <id>.scene.json` line instead of `Motion:`, `Negative:` and `Variants:`, and answers the descriptions in `descriptions` for `POST /api/import/preview` and `/confirm`; at most 6 scenes per call and a scene whose description does not pass is left out with a warning. `project` (optional, an existing project) gives the design, tempo and frame the descriptions are written for. A server with it lists `dataset` in the `features` of the catalog, and `blender` when it writes 3D scenes.

## 3D models

`POST /api/assist/dataset` with **`mode: "models3d"`** writes up to 12 entries from one sentence ("ten objects for a roller derby team room"), each the prompt of **one object alone**: its shape, material, colour and finish, in English, up to 200 characters, with no scene, no people, no text to read and no background (the engines make a model from one picture of one object, and the server completes the prompt with the background wording when it draws the picture). `Engine:`, `Detail:` and `Variants:` lines appear only when the sentence asks for them; `Seed:`, `Image:` and `Adult:` are the person's to give and are dropped if the model writes them. The answer is checked by the import of the mode before it is returned, like the other modes, so what comes back previews with nothing left out. An entry that names people, a crowd, a landscape or a scene is written again once as one object (`kind: model3d` task) and left out with a warning if it still does; `picture` and `project` are `400` for this mode, and `examples` are the presets of the kind `model3d` the caller sends (see [PROMPT_PRESETS.md](PROMPT_PRESETS.md)).

`POST /api/assist/request` with **`kind: "model3d"`** answers `{kind, kind_source: "user", title, model_prompt, language?, warnings}`: `model_prompt` is an English prompt of one object alone written from the request in any language (`"un patín de ruedas retro, rosa y brillante"` gives a description of one roller skate). The kind is the caller's alone: the model never decides it between the kinds, and an attached picture does not make a request one. When the prompt cannot be written the answer carries the kind and the title and a warning, with `model_prompt` empty; the guards are those of the other kinds.

## Examples of style

`POST /api/assist`, `/api/assist/plan` and `/api/assist/dataset` take `examples: [{prompt, negative?, tags?}]` (at most 5, each field up to 2000 characters). They are put after the task's own request as examples of the wording, length and detail to follow, with the instruction not to copy them or their subjects. A server that takes them lists `examples` in the catalog's `features`. The store of presets (`GET /api/prompts`, see [the HTTP API](http-api.md)) is where a client finds examples to send.

## Describing a picture or a clip

`veritmo describe [--model name] <file>` reads a picture (png, jpg, webp) or a clip (mp4, mov, webm, mkv, avi) with a local vision model and prints the prompt that would draw it (a second line `MOTION: …` for a clip); the model used goes to stderr:

```bash
bin/veritmo describe photo.png
```

In the editor it is "Describe a reference" next to the prompt (see the dashboard tutorial, in `dashboards-lab`); the server exposes `POST /api/describe` (see `docs/http-api.md`).

- **Descriptor.** `gemma4:26b` by default (about 12 s per picture on a 12 GB card); `--model` takes any vision model installed in Ollama.  Nothing is downloaded: install a model with `ollama pull <model>`.
- **Local only.** The file is read by your own Ollama; it is not sent anywhere and it is never used to generate: the new scene comes from the text alone (no img2img, no adapters, no face transfer).
- **Clips.** 4-8 evenly spaced frames are extracted with ffmpeg (a clip may last up to 5 minutes), described, and merged into one prompt plus a short movement prompt. The frames are deleted at the end.
- **One scene per shot.** With `--split` (in the editor: **Several scenes (one per shot)**) the cuts of the clip are found with ffmpeg's scene-change filter instead; shots under 1.5 s are merged into the previous one and there are at most 12 (it raises the sensitivity, then merges the shortest). The middle frame of every shot gets the age check and its own description and movement prompt, and the output has one line per shot, `[start-end] prompt` followed by `MOTION: …`. A single shot that looks like a minor refuses the whole clip. A clip with no cut is one scene. Measured: the 30 s skating video gave 11 shots in 40 s.
- **If the model refuses** or answers with something that is not a description, the answer says so. Nothing is invented. The refusal is the model's own.
- **Age check.** Before anything is described, every person or character in the picture (every frame, for a clip) is checked. If anyone is or looks under 18 (photographs, drawings and anime alike), or their age cannot be confirmed, nothing is described and the uploaded file is deleted. The prompts it writes always state an adult age. This is a safeguard made by a model, not a guarantee, and what you upload remains your responsibility.
- **Memory.** It needs 4 GiB of free RAM on a GPU (the weights go to VRAM) and refuses while a render is queued or active; with `VERITMO_DESCRIBE_CPU=1` it stays on the CPU and needs the model size × 1.3 + 4 GiB, and is slow with a 26 B model. The model is unloaded when it finishes.


## Shrinking long prompts with ctxpress (optional)

This is an optional feature that needs a separate compression service. The service is not part of this project and is not published with it: the server only speaks its small HTTP API (`GET /health` and the compression call), so anything that answers the same API works. Without one, everything works as it does without this feature.

If a ctxpress compression service runs on your network, every text sent to a language model (the assistant, the proposals, the part and scene writers, the reviewer) goes through it first when it is long (2000 characters by default). The HTML and CSS of animated pages use ctxpress's `animation-physics` profile, which keeps what drives layout and motion. It is off until you turn it on and it never makes a call fail: if the service is off, does not answer, refuses the token (`401`, `403`), answers `413`, `422` or `503`, or does not shrink the text, the model gets the text exactly as it was (after a failure the service is not tried again for 30 seconds; a refused token is logged without the token).

The connection is a setting like the others (the dashboard's Settings): `GET` and `PUT /api/settings/ctxpress` (`enabled`, `url`, `min_chars`, `token`) and `POST /api/settings/ctxpress/test`, which asks the service `GET /health` and a minimal compression and says `ok`, `unreachable`, `invalid_token`, `no_scope` (the token lacks the `compress` scope), `degraded` or `not_configured`. The token is kept in the private key store (`keys.json`, mode 600), like the keys of the providers, and no answer returns it (only `token_set`). A change takes effect on the next call, without a restart. If nothing is saved, the environment is the default: `CTXPRESS_URL`, `CTXPRESS_TOKEN` and `CTXPRESS_MIN_CHARS`. The text that is sent to the service is the same text that would go to the model, and a service on another machine reached over plain `http` would see the token in clear text (the settings say so in `warning`): point it at a service you trust, over `https` or a tunnel when it is not this machine.

## Other providers

The assistant, describe and the quality check can run on another provider than the built-in Ollama: another Ollama, or any OpenAI-compatible server with an API key (register them in Settings, then choose one per task in the **Tasks** card). `veritmo assist`, `describe` and `check` follow the same routing, and each accepts `--provider <id>` to use another one for that run (`check` also takes `--check-provider` on a run with `--check`).

- **Presets.** Claude and Gemini (also OpenRouter and OpenAI) come ready: `POST /api/providers {"preset": "anthropic", "key": "…"}` fills the address and suggested models (`GET /api/providers/presets` lists them with where each key comes from). Anthropic: `https://api.anthropic.com/v1/`, key from the Claude console, models `claude-sonnet-5-5` or `claude-opus-5-5`; its OpenAI-compatible layer is meant for testing, does not honour `response_format` (the writers tolerate JSON inside prose), has thinking off and does not list models. Gemini: `https://generativelanguage.googleapis.com/v1beta/openai/`, key from Google AI Studio, models `gemini-pro-latest` and `gemini-flash-latest` (aliases Google keeps on its current Pro and Flash; the exact names, such as `gemini-2.5-pro` or a 3.x one, come from the provider's list and can be typed instead); its list names carry a `models/` prefix that is removed. The names were checked on 2026-11-16 and are suggestions: edit them. **Test** sends one short chat and times it (`chat_ms`), so a key without credit or a model that is gone fails there, not later; the model list is only a convenience. Once a preset provider tests well, `GET /api/routing` shows it as `suggested` for `motion_graphics` and `quality`; nothing is routed until you do it. Cost: a model that thinks (Gemini Pro) bills the thinking as output, so a 15-scene batch with two attempts costs several euros with `gemini-pro-latest` (the one measured on 2026-11-16 used up a cap of about 10 € together with a wasted first batch) and a fraction of that with `gemini-flash-latest`; set a spending cap in the provider's console before running one. The public edition accepts only the preset hosts.
- **Consent.** A provider that is not this computer receives your pictures, clips or texts. Routing a task to one needs your explicit acceptance in Settings, tied to its address; the terminal cannot give it, so `--provider` with a remote provider you never accepted stops with a message that says to accept it in Settings.
- **No automatic fallback.** If a provider refuses, fails or is rate limited, you get the error. Nothing is sent to another provider unless you ask. After a refused description the editor lists the other providers and models to retry with.
- **Same safeguards.** The age check, the refusal detection, the deletion of refused files and the minors rule do not depend on the provider. A model that cannot read pictures says so.
- **Ollama-only rules.** Staying on the CPU, the memory check, the VRAM verification and unloading apply only to Ollama providers. A cloud provider has none of them, so it does not wait for a render either.
- **Cap.** A job on a remote provider makes at most 60 calls by default (a picture is 2; a clip as one scene 2 per frame plus 1; one scene per shot up to 3 per shot); a bigger one is refused before any call.
